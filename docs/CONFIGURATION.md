# Configuration reference

Everything about a sonar and about a simulated scenario is in a YAML file. Nothing in the
code is specific to one sonar. This page lists the keys; `docs/DESIGN.md` shows what the
owner's designs set them to and what follows.

- Sonars: `configs/sonars/<name>.yaml`, loaded with `SonarModel.load(name, overrides)`.
- Scenarios: `configs/scenarios/<name>.yaml`, run with `run_scenario(name)` or
  `tools/gallery.py --only <name>`.
- Any file may start from another with `base: <name>`; nested keys merge.
- A scenario changes its sonar with `sonar_overrides:`, using the same keys.
- Frame: x ahead (north), y to starboard (east), z down. Body frame the same on the vehicle.

## Changing a design without editing files

```python
from gpusonar.sonar import SonarModel
from gpusonar.config import load_scenario_config
from gpusonar.sim import run_scenario

# A forward-looking array with twice the elements and a 10 degree beam tilted 6 degrees up.
fls = SonarModel.load("fls_330k", {"array": {"count": 256},
                                   "fov": {"vertical_deg": 10.0, "tilt_up_deg": 6.0}})

# A longer SAS receive array (1.81 m, the MINSAS 180 class): 80 elements instead of 48.
sas = SonarModel.load("sas_minsas120", {"array": {"count": 80}})

# A Popoto array of 64 hydrophones: eight boards follow automatically.
popoto = SonarModel.load("popoto_array", {"array": {"count": 64}})

# The same scenario with another array size, speed or target.
cfg = load_scenario_config("popoto_far_mover", {"sonar_overrides": {"array": {"count": 16}},
                                                "platform": {"velocity": [2.5, 0, 0]}})
result = run_scenario(cfg)
```

## Sonar files

| Key | Meaning |
| --- | --- |
| `name`, `mode` | `mode` is `fls`, `sas` or `flank` (which processing the record is meant for) |
| `nominal_sound_speed` | m/s, used for wavelengths and default beamwidths |
| `unconfirmed` | list of keys whose values are placeholders until hardware confirms them |

### `fov` (optional): field of view in one place

| Key | Meaning |
| --- | --- |
| `fov.horizontal_deg` | full width at half maximum of each element and of the transmit beam in azimuth |
| `fov.vertical_deg` | the same in elevation |
| `fov.tilt_up_deg` | both boresights tilted up from the horizontal `array.boresight` (negative looks down) |

An explicit `beamwidth_az` / `beamwidth_el` under `array` or `transmit` wins over the block.

### `array`: the receive elements

| Key | Meaning |
| --- | --- |
| `array.layout` | `uniform_line` (default), `line` (positions along one axis), `stacked_lines` (parallel rows at different heights) or `explicit` (x, y, z each) |
| `array.rows` | for `stacked_lines`: one entry per row, `{up, out, along}` in metres (towards the vehicle's top; along the boresight, for a curved hull; along the axis), optionally its own `count`, `pitch` or `positions`. Channels run row by row |
| `platform: {name, span_m, height_m, mounting}` | what there is to mount on (the test AUV's hull, the static drop-in frame, the 2 m × 9 m face): read by the studies, the diagrams and the tests, not by the processing. On the face also `usable_span_m` and `row_baseline_m` (the owner's working values: rows within 7 m, outer rows 1.5 m apart); on the static array `static: true` and `depth_m` |
| `array.interleave` | for `stacked_lines`: take this many channels from each row in turn instead (4 with two rows and boards of eight: a board then holds the same stations of both rows and they share its clock) |
| `array.count`, `array.pitch` | number of elements and spacing (m) of a uniform line |
| `array.positions` | for `line`: metres along the axis; for `explicit`: `[x, y, z]` per element |
| `array.axis` | direction the elements run along, body frame |
| `array.boresight` | direction the elements face, body frame |
| `array.origin` | offset of the array centre from the vehicle reference point |
| `array.element_width`, `array.element_height` | element size (m); beamwidth is 0.886 λ / size when not given |
| `array.beamwidth_az`, `array.beamwidth_el` | element beamwidths (rad); absent and no size means omnidirectional |
| `array.layouts`, `array.layout_choice` | several named layouts for one board (for example dense and sparse); keys beside `layouts` override the chosen one |

### `transmit`

| Key | Meaning |
| --- | --- |
| `transmit.kind` | `point` (a projector) or `plane_wave` |
| `transmit.lever_arm` | projector position, body frame |
| `transmit.boresight`, `transmit.direction` | where the projector faces; plane-wave direction |
| `transmit.aperture_width`, `transmit.aperture_height` | projector size; or `beamwidth_az`, `beamwidth_el` directly |
| `transmit.waveform.type` | `lfm`, `cw` or `gaussian` |
| `transmit.waveform.f_start`, `f_stop`, `duration`, `window_alpha` | band (Hz), pulse length (s), edge taper |
| `transmit.waveform.source_level_db_rms` | source level, dB re 1 µPa at 1 m, **RMS** (the rms pressure of the pulse while it is on: the usual datasheet figure, and what the sonar equation uses against rms noise). With `receive.sensitivity_db` it makes samples volts: the pulse's PEAK at the ADC is √2 · 10^((SL + sensitivity + gain) / 20) (`sonar.peak_pressure_at_1m`, the one place the √2 is applied). `source_level_db` is the deprecated name of the same number: read as RMS, with a `FutureWarning` (D-102) |
| `transmit.waveform.amplitude` | PEAK echo amplitude of a 0 dB target at 1 m when the chain is uncalibrated |
| `transmit.waveform.type: sampled` | a pulse given by samples (`gpusonar/sim/waveform.py`); `f_start`, `f_stop` are then the occupied band and are required. Echoes of a sampled pulse are synthesised by the C++ kernel (host or CUDA), or by the NumPy reference when that engine is selected; `table_factor: 0` or more than 32 `gain_knots` runs in NumPy, with a warning |
| `transmit.waveform.source` | for `sampled`: `lfm`, `hfm`, `stepped_fm` (with `steps`), `barker` (with `code`: its length), `mseq` (with `degree`, optional `taps`), `code` (with `code`: chip values, or `[re, im]` pairs), `samples` (inline list), `file` |
| `transmit.waveform.file`, `dataset` | `.wav` (real passband), `.npy` or HDF5 dataset (real passband, or complex envelope) |
| `transmit.waveform.samples`, `sample_rate`, `carrier` | inline samples (real passband, or `[re, im]` pairs of the envelope), their rate (Hz; a WAV file has its own), and the carrier removed from complex samples (default: the band centre) |
| `transmit.waveform.rolloff` | phase codes: fraction of the band over which the chips' spectrum is rolled off to zero (0.25) |
| `transmit.waveform.normalise` | `peak` (default: unit peak envelope, so `amplitude` keeps its meaning) or `none` |
| `transmit.waveform.oversample` | envelope samples per cycle of bandwidth for built-in sources and the least for files (8) |
| `transmit.waveform.interp_taps`, `interp_window`, `interp_beta` | interpolator: taps (16), `kaiser` (default, shape 12) or `hann` (TR 0702 eq. 17) |
| `transmit.waveform.gain_knots` | frequency intervals across the band for frequency-dependent absorption and beam patterns (8; 0: at the band centre) |
| `transmit.waveform.replica_sample_rate` | rate of the real replica stored in the record (default 4 × the top of the band) |
| `transmit.direct_path` | absent or `false` (default): as before. `true`: the simulator adds the pulse as the hydrophones hear it straight from the projector at `transmit.lever_arm` (`sim/sources.py` `direct_arrival`): each element's own distance for the level (source level, 1/r), delay and phase (the array's near field), the element patterns, the projector's pattern per element when it has one, and the surface and bottom images when the scenario's provider has boundaries. `{boundaries: false}`: the straight arrival only. Analytic pulses: the C++ kernel on both engines; sampled pulses: C++ or NumPy by engine. Matters when the receive window includes the pulse, or with `receive.overload` |

### `receive`

| Key | Meaning |
| --- | --- |
| `receive.kind` | `real` (passband samples) or `baseband` (complex, already down-converted) |
| `receive.sample_rate`, `adc_bits`, `adc_full_scale` | sampling |
| `receive.sensitivity_db`, `gain_db` | hydrophone sensitivity (dB re 1 V/µPa) and front-end gain |
| `receive.window.range` | `[near, far]` in metres: the receive window |
| `receive.tvg` | analogue gain ramp: `time` and `gain_db` knots |
| `receive.gain_ramp` | a named hardware ramp instead (`gpusonar/hardware.py`) |
| `receive.mux.groups` | which elements each transmit captures, when fewer channels than elements |
| `receive.board_size` | channels per capture board; boards are created to fit `array.count` |
| `receive.boards` | boards spelled out, each `{first, count, clock_offset, clock_drift_ppm, jitter_rms, reference_channel}`: the board's channels are `first` to `first + count − 1`; `clock_offset` (s, 0: the board's first sample is late by this against true time), `clock_drift_ppm` (ppm, 0: its sample clock runs fast by this; t = start + offset + n / (fs (1 + drift))), `jitter_rms` (s, 0: a fresh Gaussian offset on top of `clock_offset` every ping), `reference_channel` (the channel row in the record that carries the reference; absent: none, and `sync` refuses the board). Offsets, drifts and jitter are applied by the simulator (`sim/simulator.py` `_set_board_clocks`) and are the truth `sync` has to find |
| `receive.reference` | the shared synchronisation signal wired to every board (`sim/receiver.py` `add_reference_signal`): `mode` (`sync_chirp`, the only one simulated; another value, or none, is an error), `channels` (one element index per board, the input the reference is wired to), `dedicated` (true: those inputs carry no hydrophone and are dropped after synchronisation), `f_start`, `f_stop` (Hz: a Hann-windowed linear chirp), `duration` (s, each burst), `level` (V peak at the ADC, in the record's sample units), `lead` (s from the window's opening to the first burst), `tail` (s from the end of the second burst to the window's close); for the chain also `min_quality`, `search_time` (s), `tolerance_us` (µs) and `clip_level` (V): the `sync_*` keys of `sonar_live` below. Two bursts per ping, one near each end of the window |
| `receive.overload` | absent (default): the receiver as before. Present (even empty): a behavioural front end that clips and recovers (`sim/receiver.py` `apply_front_end`; `PHYSICS_NOTES.md` Sec. 21), NumPy on both engines, real (passband) records only. **No key below defaults to a hardware value**; example values in the scenarios and tests are illustrative. With `transmit.direct_path` the time from the transmit to the opening of the window is simulated too (direct arrival only), so the window starts in the state the transmit left. The truth (per-channel overload, intervals) is in `ScenarioResult.front_end`, `simulate_ping(front_end_truth=...)` and the simulator taps, never in the record |
| `receive.overload.preamp: {limit_v, gain_db, dead_time, dead_output, recovery_tau, scope}` | the input stage, modelled only when given. `limit_v`: its output swing in volts at its output, required (one number, or `[negative, positive]` magnitudes for unequal rails); `gain_db`: the part of `receive.gain_db` up to that output (default: all of it); `dead_time` (s, 0): after its last clipped sample the output stays on that rail (`dead_output: rail`, default) or at zero (`zero`); `recovery_tau` (s, 0): the gain then returns as 1 − exp(−t/τ); `scope`: `channel` (default) or `board` (the dead time and recovery are shared by all channels of a capture board) |
| `receive.overload.highpass_corner_hz` | the AC coupling between the input stage and the ADC, modelled only when given: a one-pole high-pass. A clipped burst whose output has a mean (unequal rails, a rail held through a dead time) leaves a charge that decays with 1/(2π f) and can hold the ADC on its rail |
| `receive.overload.adc: {limit_v, clip, dead_time, dead_output, recovery_tau, scope}` | the ADC stage: clips at `receive.adc_full_scale` (or `limit_v`; `clip: false` removes the stage); the other keys as for `preamp` |
| `receive.overload.gain_switch: {gain_db, until, ramp, report}` | transmit-time gain switching, the mitigation to compare: the input gain is changed by `gain_db` (required, negative) until `until` seconds after the transmit (default: the pulse length) and returns linearly in dB over `ramp` seconds. `report: true` (default) writes it into the record's existing gain-ramp fields, which `apply_tvg` undoes (the live chain does not); not together with `receive.tvg` unless `report: false` |

## Scenario files

| Key | Meaning |
| --- | --- |
| `sonar`, `sonar_overrides` | which sonar, and changes to it |
| `fidelity` | `free_field`, `image_source` (flat surface and bottom, walls; opt-in a tilted bottom and walls as any plane), `sediment` (refraction into the bed), `eigenray` (Bellhop, external), `eigenray3d` (Bellhop3D over a 3-D bed, external, opt-in: only the illustrative `flank_seamount_3d` uses it; keys below) |
| `propagation` (`image_source`): the bottom | `bottom_z` and `bottom` come from the environment. A bottom with no description (no environment `bottom`, no `propagation.bottom`, no explicit `bottom_coefficient`) is an ERROR: no reflection coefficient is assumed (before D-104: 0.5 at every angle). `bottom_coefficient: 0.5` still gives a constant; a wall needs its `coefficient` |
| `propagation.max_order` (`image_source`), `propagation.max_arrivals` (`eigenray`) | how many bounces / arrivals per point are kept. Given: honoured. Left out (D-105): by energy: bounce orders (arrivals) are kept while one lies within `arrival_floor_db` (20 dB) of the point's strongest, up to `max_order_cap` (8) / `max_arrivals_cap` (64). When the cap cuts something above the floor a `RuntimeWarning` says how much (once per provider; `provider.truncation`); `order_used` / `arrivals_used` and (Bellhop) `dropped_energy` say what was done. Before D-105: two bounces, the strongest eight arrivals, silently |
| `propagation.walls`, `propagation.bottom_slope`, `propagation.wall_order` (`image_source`; sonar-0nsi) | Walls in two forms. `{axis: 0 \| 1, position, coefficient}`: a vertical plane x or y = position, added once to every image of the surface and bottom series with no check that the path meets it (as before; the only form the C++ provider takes). `{point: [x, y, z], normal: [nx, ny, nz], coefficient[, bounds: {x: [lo, hi], y: [..], z: [..]}]}`: any plane, `normal` into the water, unbounded unless `bounds` is given. Opt-in with that form or with `bottom_slope: [dz/dx, dz/dy]` (the bottom's depth is `bottom_z` + dz/dx x + dz/dy y, the convention of a scene `seafloor`'s `slope`; `bottom_z` is the environment's water depth, the depth at x = y = 0): every plane is a mirror of one construction that keeps only valid paths (`docs/PHYSICS_NOTES.md` section 30). `wall_order` (default 1) caps wall bounces a path; `max_order` and the energy rule count surface and bottom bounces. Refused: the two wall forms together; `wall_order` without a `{point, normal}` wall or `bottom_slope`; `bottom_slope` without a bottom; `time_spread` with either; bottom reverberation over a non-zero slope. An unknown key of a wall or of its `bounds` is refused with the nearest known key. Runs in NumPy whatever the engine. Default: absent, nothing changes |
| `propagation` | options of that tier (boundary depths, bottom properties, bounce order, Bellhop grid, arrivals kept, wind). For `eigenray`: `environment: {depth, ssp_depth, ssp_speed, bottom_speed, bottom_density, bottom_attenuation, bathymetry, ssp_range, ssp_speed_by_range}` is the ocean (sound-speed profile, bottom type, depth; `bathymetry` and the last two make the bed and the water functions of range from the sonar: "Water that changes with range" below). Bellhop's grid and fan (`sim/bellhop.py` `BellhopProvider`): `frequency` (Hz; default the sonar's band centre) and `max_range` (m; default 1.1 × the range at the close of the receive window), both filled by `environment.py` when left out; `range_step` (m, default `max_range` / 200) from `min_range` (m, 1) to `max_range`; `depth_step` (m, default the ocean depth / 50; receiver depths from half a step down to the bottom); `n_beams` (Bellhop's NBEAMS; 0, the default, lets Bellhop choose); `angles: [first, last]` (degrees, launch angles from the horizontal, Bellhop's ALPHA1 and ALPHA2; default [−80, 80]). A field point between grid nodes takes the nearest node's arrivals with a first-order delay correction |
| `time_spread` | time spreading of bounce paths (`sim/timespread.py`, D-62): `surface: {wind_speed}` or `{rms_height, mean_square_slope, rms_vertical_speed}`, `bottom: {rms_height, mean_square_slope}`, `taps` (6), `coherence_length` (10 m), `min_spacing`, `incoherent: false` for coherent loss only; `frequency` (Hz, default the sonar's band centre: where the coherent loss, the Doppler width and a bubble-loss model are evaluated); `seed` (the taps' random draws; default the scenario's top-level `seed`). Absent: bounce paths are fully coherent |
| `reverberation` item `{model: volume, layer: [top, bottom], sv_db}` | a volume-scattering layer (fish, plankton, bubbles) as SST's sheet at the layer's centre: strength per unit area = volume strength × thickness |
| `reverberation` item `{model: fluid_sediment, boundary_z, rho, nu, delta, w2, gamma2, sigma2}` | bottom scattering from interface roughness and sediment volume (`sim/bottom.py`, D-63) in place of Lambert's law. All six are needed; none has a default |
| `reverberation` item `geometry: bistatic` | take the transmitter's and the receiver's own positions and velocities (`sim/reverb_bistatic.py`): iso-time ellipses, scattering strength at the true grazing angles and bistatic azimuth (`fluid_sediment` uses the azimuth; Lambert and `volume` do not depend on it; `chapman_harris` is a backscatter fit used at the mean grazing angle), Doppler of each platform along its own ray, arrival elevation in the steering to the hydrophones. Default `monostatic`: the transmitter is taken to be at the array centre, moving with it. With `bistatic`: `n_elevation` (9) bins of arrival elevation, `max_doppler_bins` (128; the arrival directions are split by total Doppler shift in bins half the pulse's resolution 1/T wide, at most this many, so that eigenray pairs and times with different shifts keep their own), `azimuth_subsamples` (1) azimuths evaluated per sector |
| `reverberation` item `strength_map: {range: [...], offset_db: [...], azimuth_deg: [...], origin: [north, east]}` | a boundary whose strength varies over it: dB added to the scattering strength against horizontal range (and azimuth, degrees from north towards east) about a point fixed in the world; `offset_db` is `[ranges]` or `[azimuths][ranges]`, interpolated linearly, held beyond the last range. Needs `geometry: bistatic`. The boundary stays flat |
| `reverberation` item `statistics: {model: k, shape, cell_time, cell_azimuth_deg}` | K-distributed reverberation: a gamma texture of unit mean and the given `shape` per resolution cell on the Gaussian speckle (mean power unchanged; `shape` has no default; large `shape` is Rayleigh). A cell is `cell_time` long (default 1/bandwidth of the pulse) and `cell_azimuth_deg` wide (default wavelength / array extent of the receive hydrophones, rounded to whole generator sectors). Default `{model: rayleigh}`. Any other key is refused with the nearest known one |
| `reverberation` item `statistics: {model: k, scatterers_per_m2: N}` or `{model: k, patches_per_m2: N}` (in place of `shape`; exactly one of the three) | the shape of each cell from a density (Abraham and Lyons 2002 eqs. 15, 19): N x cell area / 2 for discrete scatterers, N x cell area for patches; cell area = azimuth width x slant range x c `cell_time` / 2 (flat boundary, straight paths; PHYSICS_NOTES 14.4), so the shape grows with range and with the cell. No default and no value known for any seabed: N must come from data. Warns where a cell holds fewer than one. Example: popoto_8, 2 ms CW (cell 1.5 m), `cell_azimuth_deg: 5`, `scatterers_per_m2: 1.0`: shape 6.5 at 100 m, 13.1 at 200 m |
| `reverberation` item `scatterer_motion: {velocity: [n, e, d], rms_speed, rms_vertical_speed, wind_speed}` | scatterers that move (needs `geometry: bistatic`). `velocity` (m/s, world): their mean velocity (surface drift, a current carrying a volume layer), shifting each cell by `-f/c V·(a_in + a_back)` (TR 0702 eq. 72). `rms_speed`: random motion on every axis (volume scatterers); `rms_vertical_speed`: vertical only (a heaving surface); `wind_speed` sets the latter to the rms vertical speed of a fully developed wind sea (the `time_spread.surface` parameter of the same name describes the same sea for forward bounces). They spread each direction's Doppler into a Gaussian of width `(f/c) sqrt(rms_speed² |k|² + rms_vertical_speed² k_z²)`, `k = a_in + a_back` (2 for backscatter). No drift is derived from the wind: give `velocity`. A spread below 1/20 of the pulse's own resolution 1/T changes nothing |
| `reverberation` item `bathymetry: ...` | a seabed with relief in place of `boundary_z` (needs `geometry: bistatic`; `sim/bathymetry.py`): `{plane: {depth, slope: [dD/dx, dD/dy], point: [x, y]}}`, a grid `{x: [...], y: [...], depth: [[...]]}` (`depth[x][y]`), or `{range: [...], depth, azimuth_deg: [...], origin: [x, y]}` about a fixed point; depths positive down, held beyond the tables' edges. Each cell is at its own depth with its facet's true area, grazing angles and bistatic azimuth in the facet's frame; cells hidden from either platform by nearer relief, or turned away, return nothing (`shadowing: false` turns the hidden test off). Legs with a bottom bounce before the cell are left out by default (`bottom_bounces: flat` keeps them as flat-bottom image paths, an approximation); with the `eigenray` tier Bellhop is run once per azimuth sector over that bearing's depth profile instead (transmitter and receiver over the same point); that run cannot turn rays out of the bearing's plane, so a `RuntimeWarning` names the bearings where the bed slopes across them enough to turn a ray grazing it at 10° by more than 1.8° (half the long-range arrays' 3.6° beam; `reverb_relief.CROSS_SLOPE_*`), and the provider keeps the largest turn as `cross_slope` (a warning only: no number changes; docs/tasks/PROPAGATION_3D.md P1). A level bathymetry is the flat calculation exactly |
| `bathymetry` (top level of a scenario) | one bed for the whole scenario (D-73's one description; `sim/bathymetry.py` forms): it is the `eigenray3d` provider's `propagation.bathymetry`, every bottom `reverberation` item's `bathymetry` (not volume or surface items, not one with a typed `boundary_z`) and every scene `seafloor` item's `bathymetry`; one of those typed beside it must be the same. The other propagation tiers do not see it (their bed stays flat or a range profile). No shipped scenario but `flank_seamount_3d` has it |
| `propagation` for `fidelity: eigenray3d` | Bellhop3D (`sim/bellhop3d.py` `Bellhop3DProvider`; GPL-3, run as a separate process; `GPUSONAR_BELLHOP3D`). The same `environment: {...}` ocean as `eigenray` (one profile: `ssp_range` and a range-profile `bathymetry` are refused; `depth` is the deepest water), and `bathymetry` (a `sim/bathymetry.py` description: `{seamount: {...}}`, `{plane: ...}`, a grid; absent: level), `frequency`, `max_range`, `range_step` (`max_range`/200), `depth_step` (depth/50), `min_range` (1), `bearing_step` (0.5°), `n_alpha` (241; fewer is refused: the hat-beam count found converged), `angles` ([−30, 30]°), `n_beta` (361), `azimuth_span` (120° about the points' mean bearing), `grid_step` (12.5 m: the bed's grid), `max_arrivals`, `arrival_floor_db` (20), `max_arrivals_cap` (64), `wind_speed`, `max_file_mb` (300: a run whose arrivals would exceed it, at 10 kB a receiver, is refused with the estimate), `track_tolerance` (1 m), `timeout` (s). It runs only the receivers the points need (their nodes), twice a source position (arrivals and TL; the eigenrays are scaled to the TL), about 3 s on a level bed and 20 to 90 s over a seamount a run on the CPU. An unknown key is refused with the nearest one |
| scene item `seafloor` with `bathymetry: ...` | the same description for a point-scatterer seabed: points at the bed's depth with its facet normals, amplitudes scaled for the facet's true area (`depth`, `slope`, `ripples` are then not used) |
| `reverberation` item `band_taper: true`, `guard: seconds` | against leakage of the strong start of a long record into its weak end in the reverberation generator (matters when the reverberation falls by more than about 50 dB across the record): roll the pulse spectrum off above half the generation rate's Nyquist frequency and generate two pulse lengths (or `guard` seconds) of silence after the record. Off by default so that earlier results do not change |
| `time_spread.surface.bubble_loss_db` | energy absorbed by near-surface bubbles at each surface bounce: dB, or `{grazing_deg: [...], loss_db: [...]}`. No wind law is built in |

### Background

| Key | Meaning |
| --- | --- |
| `reverberation` | a list of boundaries: `{boundary_z, mu_db}` (Lambert) or `{boundary_z, model: chapman_harris, wind_speed}`. Without `mu_db`, a model or a sediment the Lambert parameter is -29 dB (D-89; -27 dB before): the deep-water value at 530 and 1030 Hz (Mackenzie 1961 as quoted by Muggleworth, NPS 1994, hdl 10945/28529, p. 34), not a sonar-frequency one, so name a sediment (`{model: fluid_sediment, sediment: ...}`, `{sediment: rock}`) or give the site's `mu_db`; the bare default warns once at 10 kHz and above. Every shipped scenario gives `mu_db` and is unaffected. Fixed in the world: a moving sonar sees it Doppler shifted by bearing, through its own beam patterns. `offset_db` moves a boundary's strength whatever its model (what `tools/calibrate_sim.py` writes). Per item also `n_azimuth` (azimuth sectors around the sonar; default two per beamwidth λ / extent of the array, at least 72: `sim/reverb.py` `default_azimuth_count`) and `max_range` (m; default the range at the close of the receive window, c t_end / 2). A surface modelled by a `sea_surface` scene item must not also be listed here |
| `receiver.ambient_noise` | `{level_db}` flat, or `{model: wenz}` for the four-term ambient fit with the environment's wind and shipping (`{wind_speed, shipping}` typed here are checked against the environment) |
| `receiver.ambient_noise.coherence` | between hydrophones: `isotropic` (default: sin(kd)/(kd) at each frequency), `surface` (noise made at the sea surface, the Cron-Sherman model: `noise.surface_noise_coherence`; deep uniform water only) or `independent`. Real-passband and baseband records alike (D-103) |
| `receiver.ambient_noise.spectrum` | `shaped` (default: the configured spectrum across the record's band) or `flat` (its level at the centre frequency). `coherence: independent, spectrum: flat` is what every baseband record had before D-103, sample for sample: array gain against sea noise was then 10 log N whatever the pitch. Alpha-stable noise and K noise without a `correlation_time` are white and independent by construction and ignore both keys |
| `receiver.ambient_noise.statistics` | non-Gaussian ambient noise (`sim/noise.py`). `{model: k, shape, correlation_time, common}`: K-distributed; without `correlation_time` TR 0702's KNoise (a K variate per sample and channel, then the spectrum filter: kurtosis 3/shape for a white spectrum only); with it a unit-mean gamma texture held over cells that long on the Gaussian noise (spectrum and array coherence kept), shared by all hydrophones unless `common: false`. `{model: alpha_stable, alpha}`: impulsive symmetric alpha-stable samples, white in band, independent channels; for alpha < 2 there is no variance and the configured level sets the scale (that of the Gaussian noise of the same spectrum; identical to it at alpha = 2). | `receiver.ambient_noise: {model: fitted, file, gain_db, channels, include_tones, allow_uncovered}` | noise generated from a model fitted to a multichannel recording by `tools/fit_noise.py` (`sim/noise_fit.py`): its spectrum, the coherence between hydrophones and its tail. Levels are in the recording's sample units; `gain_db` (0) rescales. The model's channel count must match the sonar's, or `channels` picks a subset; frequencies the recording did not cover are refused unless `allow_uncovered` (zero noise there); `include_tones` (false) adds back the lines the fit removed |
| `sources` | radiating sources heard one way (`sim/sources.py`): a list of `{label, origin (or position), velocity, heading_deg, turn_rate_deg, signal}`; `signal` is one mapping or a list. `{type: noise, level_db, slope_db_per_octave, reference_frequency, band}` or `{type: noise, spectrum: {frequency, level_db}}` (dB re 1 uPa^2/Hz at 1 m); `{type: tonals, lines: [{frequency, level_db, phase_deg}], family: {fundamental, harmonics: [[n, 20 log A_n, phase_deg]]}}` (rms source level for a line; TR 0702 eq. 29 for a family); `{type: waveform, waveform: {...}, source_level_db_rms, times | repeat: {first, interval, count} | ping_offset}` (any transmit waveform; default the sonar's, emitted with each ping; `source_level_db_rms` is the RMS level, dB re 1 µPa at 1 m, and the deprecated `source_level_db` is read as the same number with a `FutureWarning`, D-102); `{type: file, path, dataset, sample_rate, level_db | scale, start, loop}`. Levels use `receive.sensitivity_db + gain_db` as ambient noise does. Pulses run in the C++/CUDA kernel, the rest in a NumPy streaming synthesiser |
| `sources[].stream: {knot_interval, oversample}` | the streaming synthesiser of continuous one-way signals (`noise`, `tonals`, `file`): the retarded time is solved exactly every `knot_interval` seconds (0.004) and the delay read linearly between, which is off by h² v_t² / (8 r c) seconds for a source passing at range r with speed v_t across the line of sight; `knot_interval: auto` halves the spacing until that is under 0.01 rad at the top of the band, and a fixed spacing that leaves more than 0.1 rad warns. `oversample` (2): the emission-time series is held at this multiple of the record's rate |
| `pings.transmit: false` | a passive capture: no echoes, reverberation or transmit reference; the record keeps its form and length (the receive window) |
| `reverberation` item `exclude_specular: true` (or `{mean_square_slope, rms_height, reflection}`) | `geometry: bistatic` items only: take out of the scattering strength the near-specular part that `time_spread` already carries as the tail of each bounce (`sim/reverb_specular.py`). Use it when the transmitter's pulse also arrives one way over that boundary (a `sources:` entry for a separate transmitter). `true` reads the slopes and height from `time_spread` and the reflection coefficient from the provider. Refused with a warning on a monostatic item |
| `receiver.noise_rms`, `receiver.adc` | white noise at the ADC; whether to quantise |
| `synthesis.beam_floor_db` | skip paths this far down both beam patterns (speeds up narrow-beam scenes) |

## Environment: one description per site

A scenario describes its site ONCE, under `environment`, and every part of the simulator that needs a site value
reads it from there (`python/gpusonar/environment.py`). The same schema serves the build layer's `environments:`
lists (`configs/builds/environments/`, `gpusonar.depthplan`): one loader, one validator, one set of field names.
This is the simulated site, the truth the sound is made in. What a running sonar knows of the water is the live
chain's (`elevation.profile`, `libs/live/include/sonar/live/environment.hpp`) and is not set here.

```yaml
environment: {base: coastal_12c_sand, water_depth_m: 60.0, wind_speed_m_s: 5.0, shipping: 0.5, absorption: francois_garrison}
```

`environment` is a mapping, the name of an environment, or `{base: <name>, ...}` (the named one with some fields
changed). Names: a file `configs/environments/<name>.yaml` (one mapping, which may itself have a `base`), or an entry
of a list file (`environments: [...]`) there or under `configs/builds/environments/`.

| Field | Unit | Meaning | Left out |
| --- | --- | --- | --- |
| `water_depth_m` | m | water depth | no bottom anywhere |
| `bottom` | | a name in `configs/sediments.yaml`, or `{speed (m/s), density (ratio to water), attenuation (dB per wavelength)}`. Needs `water_depth_m` | the bottom reflects nothing unless a block gives its own |
| `wind_speed_m_s` or `sea_state` | m/s at 10 m; 0 to 9 | the sea surface: ambient noise, surface reverberation laws, time spreading, Bellhop's surface loss, bubble laws | no wind is given to anything; a Wenz noise spectrum then uses 5 m/s (`environment.DEFAULT_WIND_SPEED_M_S`) |
| `rms_wave_height_m` | m | rms surface displacement (significant height / 4), an input of its own: measured heights did not follow the wind law (`docs/PHYSICS_NOTES.md` Sec. 21). Given to `time_spread.surface.rms_height` | the Pierson-Moskowitz height of the wind |
| `sound_speed_m_s` | m/s | sound speed of isovelocity water; beside a profile, the speed at the sonar (what a record carries) | the profile at `reference_depth_m`; else Mackenzie/Marczak from `temperature_c`, `salinity_psu`; else 1500 (`acoustics.NOMINAL_SOUND_SPEED`, the one definition) |
| `profile` | | `{depth_m: [...], speed_m_s: [...]}`, or a family: `{family: munk[, axis_depth_m, axis_speed_m_s, points]}`, `{family: linear, surface_speed_m_s, gradient_per_s}`. Used by the `eigenray` tier | isovelocity |
| `profiles_by_range` | | `[{range_m, depth_m: [...], speed_m_s: [...]}, ...]` in place of `profile`: water that changes with range (see "Water that changes with range" below). No value is assumed: two profiles or more, the first at `range_m: 0`, ranges increasing, every profile on the same depth grid from 0 to the bottom or deeper. Used by the `eigenray` tier | the same water at every range |
| `temperature_c`, `salinity_psu`, `ph`, `reference_depth_m` | deg C, PSU, -, m | the water for absorption and for the sound-speed formula | 10, 35, 8, 0 (`environment.DEFAULT_*`; the resolved environment lists which were defaulted under `defaulted`) |
| `absorption` | | `francois_garrison`, `ainslie_mccolm`, `thorp`, `none` (a scenario's own `absorption` key wins: the model is a choice of formula, the water it is evaluated in is the site's) | `francois_garrison` |
| `shipping` | 0 to 1 | shipping activity of the ambient-noise spectrum | 0.5 |
| `bubble_model` | | wind law for the loss per surface bounce (build layer's planner) | none |
| `water_depth_known` | bool | `false`: the vehicle is not told the depth (the record's `environment.water_depth` stays unset; a processor then has it from navigation or not at all) | `true` |
| `frame_origin_lla` | deg, deg, m | written into records | |
| `overrides` | | `{field: "reason"}`: a field stated on purpose although another implies a different value (a nominal `sound_speed_m_s` beside a temperature: geometry then uses the first, absorption the second). Without it that case warns | |
| `name`, `title`, `note`, `illustrative`, `own_depth_limits_m`, `bottom_clearance_m` | | labels, and the build layer's planning fields (`docs/REFERENCE_DESIGN.md`) | |

The older spellings `sound_speed`, `water_depth`, `temperature`, `salinity`, `wind_speed`, `depth` are the same
fields (`environment.ALIASES`); one field under two spellings with different values is an error.

**Who takes what** (`environment.apply_to_scenario`; a key typed in the block is kept and checked):

| Block | Takes from the environment |
| --- | --- |
| `propagation`, `image_source` | `bottom_z` = water depth; `bottom` = the bottom (unless `bottom_coefficient` is given) |
| `propagation`, `eigenray` | `environment: {depth, ssp_depth, ssp_speed or sound_speed, bottom_speed, bottom_density, bottom_attenuation or sediment}`, and with `profiles_by_range` also `ssp_range`, `ssp_speed_by_range` (`ssp_speed` is then the local profile); `frequency` = the sonar's band centre (it follows `sonar` and `sonar_overrides`); `wind_speed`; `max_range` = 1.1 x the far edge of the receive window |
| `time_spread.surface` | `wind_speed` when the section gives no roughness of its own (`surface: true` is enough), `rms_height` = `rms_wave_height_m` |
| each `reverberation` item | `boundary_z`: 0 for the surface laws (`chapman_harris`, `kraus_surface`, `bubble_layer_surface`), the water depth for the others (`boundary: surface` puts a Lambert item on the surface); `wind_speed` for the surface laws; `sediment` for `fluid_sediment` when the bottom is a name |
| `receiver.ambient_noise` | `{model: wenz}` (or `true`): `wind_speed`, `shipping`. `{level_db: ...}` is a flat spectrum and takes nothing |
| `absorption`, and every absorption calculation | the model, and the water (temperature, salinity, depth, pH) |
| the record | `sound_speed`; `temperature`, `salinity`; `water_depth` unless `water_depth_known: false` |

**A typed value that contradicts the environment is an error**, naming the key, unless the scenario lists it:

```yaml
environment_overrides:
  propagation.wind_speed: "the eigenrays reflect from a flat surface although the site has wind; ..."
```

Keys are dotted paths (`propagation.frequency`, `propagation.environment.depth`, `reverberation[1].wind_speed`,
`time_spread.surface.wind_speed`, `receiver.ambient_noise.wind_speed`). An entry that no longer
differs gives a warning, so the list cannot go stale. Two things need no entry: an explicit null
(`propagation.bottom_z: null`: no bottom in this run), and, with `propagation.environment.bathymetry`, an ocean `depth`
deeper than the environment's water depth (the deepest point of a bed that changes with range; the environment's is the depth at the sonar).

`config.load_scenario_config(name, overrides)` returns the scenario EXPANDED: the environment resolved (with
`sound_speed`, `temperature`, `water_depth`, `site_water_depth`, `wind_speed`, ...) and every block holding the
values it took, so code that reads `cfg["environment"]["sound_speed"]` or `cfg["propagation"]["bottom_z"]` finds
them. To change the site of a loaded scenario pass the change as an override
(`{"environment": {"water_depth_m": 45.0}}`); `expand=False` gives the file as written. What the environment does
NOT reach: positions typed in `scene` and `platform` (a seabed object at `z: 60`), the `sediment` tier's
`sediment_speed` and `interface_z`, and a scene surface's own `spectrum`.

### Water that changes with range

```yaml
environment:
  water_depth_m: 100.0
  profiles_by_range:                    # range_m: horizontal distance from the sonar, m
    - {range_m: 0.0,    depth_m: [0, 15, 35, 100], speed_m_s: [1500.0, 1500.0, 1485.0, 1486.1]}     # the LOCAL profile
    - {range_m: 1200.0, depth_m: [0, 15, 35, 100], speed_m_s: [1500.0, 1500.0, 1485.0, 1486.1]}
    - {range_m: 1400.0, depth_m: [0, 15, 35, 100], speed_m_s: [1478.0, 1478.3, 1478.6, 1479.7]}
  sound_speed_m_s: 1488.75              # the local profile at the sonar's depth: what the record carries
```

`profiles_by_range` gives the `eigenray` tier a sound speed that depends on range as well as depth (a front, other water
beyond a sill, a thermocline that deepens). It goes to Bellhop as Bellhop's own 2-D field (SSP option `Q`, a `.ssp`
file beside the `.env`; `sim/bellhop.py`), so the rays bend, speed up and slow down in it; nothing of it is
approximated on this side.

| What | Rule |
| --- | --- |
| What range is | The horizontal distance from the sonar, whatever the bearing: the provider's 2-D section starts at the source of each eigenray call (the projector, the array's reference point) and is the same in every direction, exactly as `propagation.environment.bathymetry` is. The water is therefore rings about the sonar, not a front lying across a map, and it moves with a moving vehicle. A target at 2.6 km on any bearing is behind a front at 1.3 km |
| The local profile | The first profile, at `range_m: 0`: the water at the sonar, the one a cast from the vehicle gives. `environment.profile` in the resolved environment, `ssp_depth` and `ssp_speed` of the ocean, and every "the sound speed" below are this one |
| Between and beyond | Between two profiles the speed at each depth is linear in range (Bellhop's quadrilateral interpolation; linear in depth between grid depths). Two profiles with the same speeds make a stretch of unchanged water; the width of a front is the distance between the two profiles either side of it. Beyond the last range the last profile holds (as a bathymetry's last depth does) |
| Errors (no value is filled in) | fewer than two profiles; first range not 0; ranges not increasing; a profile on another depth grid than the first; a grid that does not start at 0 or does not reach `water_depth_m` (and, with a bathymetry or reverberation over relief, the deepest point of the bed); depths and speeds of different lengths; a speed outside 1300 to 1700 m/s; a key other than `range_m`, `depth_m`, `speed_m_s`; `profile` beside it; `sound_speed_m_s` outside the local profile |
| With `base` | a child's `profile` or `profiles_by_range` replaces the parent's water, whichever of the two the parent used |

What every other user of "the" sound speed does when the profile varies with range:

| User | Uses | Why, and what it costs |
| --- | --- | --- |
| The record (`environment.sound_speed`), and with it the chain | `sound_speed_m_s`; left out, the local profile at `reference_depth_m`. Set it to the local profile at the sonar's depth | what the vehicle would measure. The record's fields are unchanged: one speed, no profile. A chain is told nothing else unless its own configuration is (`chain.elevation.ssp`) |
| Apparent positions of the eigenrays (delay x speed along the launch direction) | the local profile at the source's depth | the kernel works with straight lines at one speed; delay and angle at the array are Bellhop's and are kept exactly |
| Delay correction from a Bellhop grid node to the field point | the speed at the point's own range and depth | first order in the offset from the node |
| Absorption | the environment's one water (`temperature_c`, `salinity_psu`, `reference_depth_m`, `ph`), over the path length taken as delay x the local speed | the profiles carry speeds, not temperatures; a 1 % error in path length is 1 % of the absorption in dB (0.02 dB of the 1.7 dB two-way at 2.6 km and 5 kHz) |
| Rough-surface loss of the eigenrays (`propagation.wind_speed` > 0) | the surface grazing angle by Snell's law from the launch angle through the LOCAL profile | not valid where the speed changes along the ray: at grazing angles of a few degrees a 1 % change of speed moves the angle by degrees. The shipped scenarios reflect the eigenrays from a flat surface (`propagation.wind_speed: 0` with its override) for that reason |
| `time_spread` (speeds at the surface and the bottom), reverberation strength laws, `reverb_specular`, the basin tail, noise coherence, `sediment` named bottoms (speed ratio x the bottom-water speed) | the local values | these are properties of a boundary patch or of the array's own water; the patch's water is up to 1.5 % off in the shipped scenarios |
| Reverberation's paths, one-way sources, the direct arrival | Bellhop through the 2-D field (they ask the same provider) | |
| `fidelity: image_source`, `free_field`, `sediment` | the environment's one sound speed everywhere, with a warning that the change with range is NOT simulated | these tiers have no profile at all |
| The depth planner (`gpusonar.depthplan`) | the local profile at every range; the plan's `method` and `profile_rests_on` say so | the planner is range independent |

### Steps of a chain file: keys derived from the record, and where the defaults live

A step passes on only the keys its config gives; every other parameter takes the default of the function it
calls (`recon.sas_image`, `recon.fan_image`, `recon.stripmap_grid`, `motion.MotionOptions`), stated there once.
Keys added by the audit of hard-coded assumptions (`HARDCODED_AUDIT.md`); each default reproduces the earlier behaviour:

| Key | Meaning |
| --- | --- |
| `{stage: tvg}`: `spreading` | `two_way` (40 dB per decade: an echo; the default), `one_way` (20: a passive or transponder arrival), `auto` (two-way when the record has a transmit pulse) or a number. The older `spreading_db_per_decade` still works |
| `{stage: tvg}`: `absorption` | absent or `auto` (the default, D-91): Francois-Garrison at the record's centre frequency for the temperature and salinity the record states; a record that states neither gets no absorption and one `RuntimeWarning` per process naming the missing fields, so older records still process. `record`: the same derivation, but a record without the two fields is an error. `none`: 0 dB/m, the law before D-91 exactly. A number: dB/m **one way** (the law doubles it); the older `absorption_db_per_m` means the same. At 330 kHz and 12 °C it is 0.083 dB/m: without it the law is 51 dB short at 307 m. With `auto` or `record`: `temperature`, `salinity`, `depth`, `ph` (8.0), `model`, `frequency` override or supply what the record gives. `core.apply_tvg` called directly (C++ and its binding) still defaults to none: it has no model of the water |
| `{stage: tvg}`: `max_gain_db`, `reference_range`, `undo_hardware_ramp` | the clamp (120 dB), the range of 0 dB (1 m), whether the recorded analogue ramp is divided out first (true). The step's log entry gives `clamped_samples`, `clamp_range_m` and `shortfall_db`: where the law was cut at the clamp and by how much at the last sample |
| `{stage: sas_image}`: `plane_z` | z (m, down) of the imaging plane, or `seafloor`: from the records (each ping's z plus its DVL altitude; without a DVL, `environment.water_depth` with the surface at z = 0; an error with neither). Default 0.0, which is the seabed only for a scenario whose origin is on the seabed. The log entry gives `plane_z` and the `seafloor_z_from_records` |
| `{stage: sas_image}`: `fov_factor`, `cull_block`, `interp`, `directivity_weight`, `replica_window`, `position_lookup`, `full_support`, `beamwidth_az` | passed to `recon.sas_image` / `recon.stripmap_grid` when given (their defaults: 1.13, 16, `sinc`, false, `none`, `analytic`, true, the element's) |
| `{stage: sas_image}`: `trajectory_allowance` | with a trajectory table (`position_lookup: software_table` or `texture`) and `fov_factor > 0`: how far the platform may stray from its first-order pose within a ping before the kernel's field-of-view pre-test rejects a pixel. ### Sizes the chain derives, and the keys of the programs around it

Settings whose right value follows from the sonar are **not typed anywhere**: left out of a deployment file they are
derived from the first ping's record (its waveform, its array and its sound speed) by one function, `libs/live`
`derive.hpp`, which both engines call. Each is the larger of a *standing value* (the number typed until now, tuned on
kilometre-range arrays with a band of 2 kHz or more) and a *floor* that follows from the sonar; a key in the file
always wins. Every shipped flank sonar gets exactly the standing values (`tests/python/test_hardcoded.py`). What was
resolved is printed once on stderr (`chain settings {...}`) and is `LiveChain.resolved` in Python, with the lists
`given` (set in the file), `scaled` (the floor decided) and `warnings`.

### `passive.tonal` (optional): Goertzel lines and DEMON when listening

Off unless given; without it the passive report lines are what they were, byte for byte.
In a deployment file it is the `tonal` key of a `passive` section (beside `f_low`, `f_high`,
`n_fft`, `hop`, `n_average`); `gpusonar.tonal.TonalAnalyzer` takes the same dictionary, and
`gpusonar.tonal.cpp_options` (and `tools/sonar_live.py --export-template`) turns it into the
program's arguments: `tonal=1` and one `tonal_<key>=value` per setting below
(`tonal_goertzel_block_s=0.5`, `tonal_demon_pfa=1e-6`; lists comma-separated:
`tonal_goertzel_lines=300,450`; `bearings_deg` as `tonal_bearing_first_deg`, `_last_deg`,
`_step_deg`; `goertzel.track` as `tonal_goertzel_track=0|1` with `tonal_goertzel_alpha`, `_beta`,
`_max_misses`, `_max_shift_hz`; `demon.band` as `tonal_demon_f_low`, `tonal_demon_f_high`;
`shaft_hz` and `blades` as `tonal_demon_shaft_min_hz`, `_max_hz`, `tonal_demon_blades_min`,
`_max`; `tonal_demon=1` switches DEMON on, giving lines switches Goertzel on).
The method and what each number in the report means: `gpusonar/tonal.py`, `DEPLOYMENT.md`.

| Key | Meaning (default) |
|---|---|
| `bearings_deg` | first, last, step of the beams lines and modulation are looked for on (`[-80, 80, 1]`) |
| `window` | aperture weighting of each row of hydrophones: `hann` (default) or `rect` |
| `row_tolerance_m` | hydrophones within this of one line are one row (0.02 m). Rows are steered separately and their powers added, so stacked arrays need no elevation |

| `goertzel.lines` | the frequencies to watch, Hz absolute (required for Goertzel; there is no search for unknown lines) |
| `goertzel.on` | `beams` (default): the array steered over `bearings_deg`, the line reported at the bearing it is strongest at; `hydrophones`: channel powers added, no bearing |
| `goertzel.block_s`, `hop_s` | seconds of data per estimate (1.0): the bins are 1 / `block_s` apart and the bin's noise bandwidth is 1.5 / `block_s`; seconds between estimates (default: `block_s`) |

| `demon.band` | `[f_low, f_high]` Hz absolute, the band whose envelope is analysed (default: the passive band, else the transmit band) |
| `demon.envelope` | `square` (default): the band's power in each block; `hilbert`: its square root (the RMS of the analytic signal over the block) |
| `demon.envelope_rate_hz`, `window_hops` | sample rate of the envelope (100 Hz: modulation up to 50 Hz, lines looked for up to 0.8 of that); each envelope sample is from a block `window_hops` (2) envelope samples long, Hann weighted. The block should be long against the travel time across the array (see `DEPLOYMENT.md`) |
| `demon.segment_s`, `segment_overlap`, `n_average`, `min_segments` | seconds of envelope per spectrum (8: modulation bins 0.125 Hz apart), the fraction shared with the next (0.5), how many of the latest spectra are averaged (8) and how many must be there before a result is given (4) |
| `demon.f_min_hz`, `f_max_hz` | modulation lines are looked for between these (1 Hz; 0.8 of half the envelope rate) |
| `demon.background_bins`, `guard_bins`, `clip` | the background of a bin is the mean of this many bins each side (16), skipping `guard_bins` (2), taken twice: the second time without the bins more than `clip` (3) times the first estimate |
| `demon.pfa` | false-alarm probability per bearing and modulation bin; the line threshold follows from it, the number of spectra averaged and the number of background bins (1e-6; a result of 161 bearings × 313 modulation bins has 50 000 cells). Measured on noise alone: 1.0e-3 to 1.5e-3 for 1e-3 asked for, about 1e-4 for 1e-4; at 1e-6 more than asked for (three false single lines in four minutes of 61 bearings), none of them forming a shaft rate |
| `demon.max_lines`, `max_sources`, `min_separation_deg` | lines kept per source (12), sources reported (4); lines closer in bearing than `min_separation_deg` (4°) are one source, and a line is reported only at the bearing it is strongest at within that distance |
| `demon.shaft_hz`, `max_harmonic`, `harmonic_tolerance_bins`, `score_fraction` | shaft rates considered (`[0.5, 30]` Hz), the highest harmonic of it a line may be (12), how far (in modulation bins, 1.0) a line may lie from a harmonic, and the fraction of the best explanation's score the highest candidate rate must reach to be taken (0.9) |
| `demon.blades` | blade counts considered (`[2, 9]`): the harmonic number of the strongest line of the set, when it is in this range |
| `demon.gram` | put the DEMONgram (dB above the background over bearing × modulation frequency, 0.1 dB steps) in every DEMON result of the report (`false`: it is large; `TonalAnalyzer.gram` and `core.TonalAnalyzerCpp.gram()` always hold the latest) |

The simulator uses its C++ path and reverberation code by default; `GPUSONAR_SIM_ENGINE=numpy`
(or `engine="numpy"` on `run_scenario`, `simulate_ping` and the providers) selects NumPy.
For a sampled transmit pulse the same switch also selects the echo synthesiser (C++ kernel
by default, NumPy reference); analytic pulses are synthesised by the C++ kernel only.

Source types and how to tap, inspect and re-inject data: `ARCHITECTURE.md`.

## Build specs, and what they add to the other files

`configs/builds/<build>.yaml` describes a build in spec-sheet terms; `tools/build_from_spec.py` generates
the sonar, deployment and scenario files from it. Fields: `REFERENCE_DESIGN.md`.

| Key | Where | Meaning |
| --- | --- | --- |
| `unconfirmed` | any sonar or scenario file | dotted keys whose values are assumptions. Through `base:` the lists **accumulate** (a child no longer hides its base's flags) |
| `confirmed` | a file with `base:` | takes flags off the inherited list: the entry itself and anything below it (`confirmed: [receive]` clears `receive.boards`). Naming a key under `unconfirmed` again puts it back |
| `platform: {name, kind, span_m, height_m, usable_span_m, usable_height_m, row_baseline_m, mounting, static, depth_m}` | sonar file | what the array is mounted on; read by the diagrams, the parts list and the validator, not by the simulator or the chain |
| `hardware: {hydrophone, boards, sync, projector, navigation, sound_speed, water_depth, compute, storage}` | sonar file | the build's parts as the spec names them (models, inputs per board, where the boards sit for cable lengths, the synchronisation scheme and its tolerance target): for the diagrams and the parts list only |
| `build` | sonar file | the spec the file was generated from |
| `receive.window` | every stage sonar file | stated in each file from the spec's `operation.range_m` (first range `null`: the pulse's blind range) |
| `truth` | generated scenarios, `popoto_12km_2row`, `_3row` | for tests and tools only: what the self-tests check reports against (`tools/build_from_spec.py --self-test`, `tests/python/test_buildspec.py`, which read and remove it before simulating). The simulator ignores it and nothing in the chain reads it. Not every member is read: `ship.first_x_m` in the two `popoto_12km_*row` files is read by no code (only `ship.range_m` is checked) |
| `GPUSONAR_CONFIG_PATH` | environment | further config trees searched after `configs/` (how a generated build is used in place); `config.add_config_dir(path)` does the same in code |
